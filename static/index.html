Getting Started

Set up and run your first stress test in under a minute

Quick Start Guide

  1. Enter a target URL — The endpoint you want to test (e.g., https://your-api.com/health)
  2. Set concurrency — How many simultaneous workers will send requests. Start with 10-50 for a gentle warm-up
  3. Adjust delay — Time between requests per worker in milliseconds. Lower = more aggressive
  4. Click Start Test — Watch the heartbeat monitor come alive
Pro tip: Use https://httpbin.org/get as a safe target to test Axion itself without hitting your own servers.

Concurrency & Workers

How concurrent workers simulate real-world traffic patterns

Worker Model

Each worker is a goroutine that continuously sends requests with a configurable delay. Workers operate independently, simulating multiple users hitting your endpoint simultaneously.

How to Choose Concurrency

Scenario Workers Delay
Smoke test 1-5 500-1000ms
Average load 20-50 100-200ms
Stress test 100-500 0-50ms
Spike test 1000+ 0ms
Estimated RPS RPS ≈ Workers ÷ (Delay in seconds) Example: 50 workers with 100ms delay ≈ 500 RPS

Heartbeat Monitor

Interpreting the real-time ECG visualization of your system's health

Reading the Heartbeat

The heartbeat visualization mimics a medical ECG monitor to give you an immediate, intuitive sense of system health:

Healthy

Strong, regular ECG waveform. Your system is handling the load well. Error rate below 10%.

Degraded

Irregular rhythm. Errors between 10-50%. Your system is struggling — consider reducing load or investigating bottlenecks.

Critical / Flatline

Weak or flat signal. Error rate exceeds 50%. Your system may be overwhelmed or unresponsive.

BPM (Beats Per Minute) is derived from your RPS. A higher BPM means more throughput — but only if error rates stay low.

Metrics Explained

Understanding throughput, latency, error rates, and success rates

Key Metrics

Throughput (RPS)

Requests per second — the number of requests your system is handling. Higher is better, but only when paired with low error rates. Watch for plateaus that indicate bottlenecks.

Success Rate

Percentage of requests that returned successfully (HTTP 2xx/3xx). Aim for 99%+ in production. Drops below 95% warrant investigation.

Error Rate

Failed requests as a percentage. Common causes: timeouts, connection refused, 5xx responses. A sudden spike often indicates your system has hit a limit.

Latency (ms)

  • Avg: Mean response time. Useful for general trends but can hide outliers
  • Min/Max: Fastest and slowest requests. Large gaps suggest intermittent issues
  • P99: 99th percentile — 99% of requests were faster than this. The metric that matters most for user experience

CLI & CI/CD Integration

Run Axion headlessly in your pipelines and automate stress testing

Headless Mode (Coming Soon)

Axion will support running without the browser UI for automated testing scenarios:

Terminal 
# Run a 30-second stress test with 100 workers
axion test --url https://api.example.com \
  --concurrency 100 \
  --delay 50ms \
  --duration 30s \
  --output results.json

# CI/CD pipeline example (GitHub Actions)
- name: Stress Test
  run: |
    axion test --url ${{ secrets.API_URL }} \
      --concurrency 200 \
      --duration 60s \
      --threshold-error-rate 5 \
      --exit-on-failure

Exit Codes

Code Meaning
0 All thresholds passed
1 Error rate exceeded threshold
2 P99 latency exceeded threshold
3 Connection failure

Configuration Reference

Complete reference for all test parameters and their effects

Test Parameters

Parameter Type Default Description
targetUrl URL — The endpoint to send requests to. Must be a valid HTTP/HTTPS URL.
concurrency Number 10 Number of simultaneous workers. Range: 1-1000.
requestDelayMs Number 100 Milliseconds between requests per worker. 0 = no delay.
durationSecs Number 0 Test duration in seconds. 0 = run until manually stopped.

Best Practices

  • Start small: Begin with low concurrency and gradually increase
  • Monitor your own resources: Generating load consumes CPU/Memory too
  • Test in isolation: Run against staging environments, not production
  • Set duration limits: Prevent accidental infinite tests in CI/CD
